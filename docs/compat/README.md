# Legacy compatibility manifest

The canonical inventory is generated by the Rust `xtask compat-scan` command from exact, read-only checkouts. It is not maintained by hand.

## Scanner contract

- Input is one or more `REPOSITORY@COMMIT@PROFILE=PATH` source specifications.
- Every checkout is expected to be detached at the specified 40-hex commit.
- The scanner ignores VCS metadata and generated dependency/build directories (`.git`, `node_modules`, `target`, coverage and Playwright outputs).
- It inventories JS, HTML, CSS, JSON, SVG/images, font binaries, text corpora/fixtures, Markdown/PDF documentation, YAML workflows and TOML build files.
- Every record has a stable profile/path identity and a SHA-256 of exact file bytes.
- Output has no timestamp or absolute checkout path. File and source order is stable, so repeated scans of the same commits must be byte-identical.

## Status semantics

The initial scanner deliberately avoids asserting behavior it has not executed:
- `verified-data`: file bytes and identity were scanned; semantic validity, license, glyph coverage and runtime use are not implied.
- `historical-only`: executable legacy source is pinned but is not automatically declared equivalent to Rust.
- `spec-only`: documentation/research source in the Typesetter_doc repository.
- `conflict`, `blocked-license`, and `verified-executable` require later explicit review/evidence; the scanner does not assign them by guess.

`verificationLevel=scanned-hash-only` is not a parity claim. The `rustOwner`, `parserOrConsumer`, `assetDependencies`, `parityFixtures` and `migrationRule` fields are intentionally left unassigned until the ownership pass (task 8).

## Regeneration

See `.github/workflows/compat-manifest.yml`. It checks out all six pinned repositories, verifies their HEAD commits, runs the scanner twice and requires byte-identical output. The generated manifest is uploaded as a workflow artifact for review and promotion into this directory.
